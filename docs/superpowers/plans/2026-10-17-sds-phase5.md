# SDS Phase 5 — Release Acceptance Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Chứng minh phạm vi 1.0 hoạt động trên Windows/mạng công ty, đóng gói và bàn giao có khả năng nâng cấp, phục hồi và hỗ trợ.

**Architecture:** Đóng băng candidate commit/config/lockfiles; kiểm thử cùng binary qua native Tauri và Store thật. Mỗi failure được phân loại baseline/regression/environment; sửa có regression test rồi tạo candidate mới. Rollback app binary và restore dữ liệu là hai quy trình riêng, không giả định DB mới chạy được với binary cũ.

**Tech Stack:** Existing npm/Cargo test/build scripts, Tauri NSIS, Windows temp profiles/VMs, dedicated local Store/database, network/proxy/CA test environment do IT cung cấp.

**Spec:** [Delivery design §3,4,8,9,11](../specs/2026-10-16-sds-app-delivery-design.md), [SRS §4–7](../../sds-phase1/SRS.md), [review và traceability](2026-10-17-sds-phase3-5-review.md), [Phase 3](2026-10-17-sds-phase3.md), [Phase 4](2026-10-17-sds-phase4.md).

Trạng thái draft. Phase 5 là test/release work, không trì hoãn test của Phase 3–4 đến đây. Paths tương đối root candidate app; `R`=`src-tauri/src/sds`, `F`=`src/features/sds`.

## Global Constraints

- Windows; internal installer release không fixtures; development artifact và internal artifact khác cấu hình và phải lưu riêng.
- Store: chỉ thêm file/folder/package mới; không sửa, di chuyển hoặc xóa file hiện có, kể cả cấu hình, dependency manifest, security hoặc migration cũ.
- Database Store: chỉ thêm bảng/job/đối tượng mới khi cần. Không sửa hoặc xóa bảng, cột, index hay đối tượng hiện hữu. Không chạy script reset/recreate DB dùng chung.
- HTTP chỉ cho loopback trong cấu hình development. Môi trường nội bộ dùng HTTPS có xác minh chứng chỉ; không cho tắt TLS verification.
- Không log token/password/MCP secrets; không public updater/Git/CLI; không tự cấu hình agent/MCP.
- Không bỏ qua fail/ignored test rồi gọi toàn suite pass. Fixture, directory inspection và real agent recognition là các mức bằng chứng khác nhau.
- AIPro không cài được trên máy pilot: giữ tiêu chí directory inspection đã chấp nhận. Corporate runtime test chỉ ghi pass khi có người/môi trường chạy thật; không tự tạo lại gate bắt buộc trên máy này.
- Không tự phát hành diện rộng, ký bằng credential chưa được cấp hoặc đổi network/security máy người dùng. Test phá lỗi chạy trên temp roots/VM/test DB thuộc task.

## Review Focus

1. Upgrade từ pilot khi còn pending journal/local edits: migration không mất references; recovery không replay operation đã commit (P5.2).
2. Uninstall/rollback xóa Library hoặc đưa DB mới vào binary cũ: bảo toàn dữ liệu và có đường restore rõ ràng (P5.2).
3. Mạng bị chặn/proxy/CA/WebView2 chưa cài: fail có hướng dẫn, không fallback Internet/TLS bypass (P5.3).
4. Fault sau rename trước DB commit/disk full/snapshot fail: không mất bản cũ, không báo success sai (P5.1).
5. Artifact đã test khác artifact bàn giao: commit/config/version/hash và chữ ký được đối chiếu (P5.4).

## P5.1 — Hồi quy chức năng, lỗi và hiệu năng

**Depends:** G2 + Phase 3–4 acceptance. **Files:** Create `docs/superpowers/testing/phase5-regression.md`, `docs/superpowers/evidence/phase5-regression.md`, `docs/superpowers/evidence/phase5-performance.md`; extend affected existing `R/tests/*` và `F/**/*.test.tsx` only where gap found. Do not add tests solely mirroring code.

**Evidence interface:** mỗi case có `caseId, requirementId, candidateCommit, environment, fixtureOrReal, steps, expected, actual, status, evidencePath, defectId`. Status `pass|fail|blocked|not-run`; không gộp blocked thành pass.

- [ ] Lập fixture matrix hữu hạn: bốn agent × global/project; ZIP/7z; Store/local; clean/modified/unmanaged/missing target; session authenticated/expired/offline/forbidden; cache valid/corrupt/missing. Chọn pairwise UI coverage và exhaustive tests cho path/commit guards, không đòi chạy mọi tích Descartes bằng tay.
- [ ] Functional acceptance: login/catalog/detail; one-target/mixed batch/preset; update selected target; local edits snapshot/restore; scoped remove; referenced-cache delete; local import; activity export; settings/onboarding/app-release. Mỗi requirement trong bảng review có ít nhất một case và evidence path.
- [ ] Fault injections trong owned roots: checksum sai, disk full/quota ở staging và snapshot, denied write, target đổi sau review, double execute, cancel trước/trong commit, kill sau intent/rename/DB commit, restart rồi retry. Assert old/selected/unselected file hashes đúng, không orphan commit được báo success. Không tạo disk-full trên volume hệ thống; dùng bounded virtual volume/test fault seam.
- [ ] Với lỗi mới: viết regression test failing ở module sở hữu, chạy chứng minh red, sửa tối thiểu, chạy green + adjacent suite; lưu defect/retest. Không sửa product chỉ để né lỗi setup upstream.
- [ ] Run tại root candidate:

```powershell
npm run test:sds
npm run lint
npm run build
npm run build:sds
npm run sds:check
node scripts/test-sds-contracts.mjs
node --test scripts/sds.test.mjs scripts/sds-fixtures.test.mjs scripts/sds-bundle.test.mjs scripts/sds-installer.test.mjs
cargo test --manifest-path src-tauri/Cargo.toml --no-default-features --features sds --lib sds::tests
cargo test --manifest-path src-tauri/Cargo.toml
cargo test --manifest-path src-tauri/Cargo.toml --features sds
```

Expected: scoped SDS/frontend/contracts exit 0; full suites zero new failures, known baseline failures still reported as fail with reason. Run full suites once per release candidate; if same setup failures persist attach baseline comparison. Live-provider/vault opt-ins require isolated credentials/setup and separate command from existing test annotations; ignored helpers are not falsely counted as coverage. If setup missing mark blocked.

- [ ] Native acceptance on installed release, not browser mock: W01–W14, 1440×860/minimum1100×640, light/dark, supported text scales, focus/tab/Esc/focus return, scrolling/long Unicode/error text. Ensure no action button is clipped, state not only color, no remote markdown/font fetch.
- [ ] Performance: dataset proposal 1,000 Library artifacts, 100 deployments, paged Store 20/100 items; record machine, versions, network latency, warm/cold cache. Measure 30 interactions and 30 catalog fetches, report median/p95 and UI responsiveness during hash/extract. SRS goals interaction≤200ms/catalog20≤2s are **proposed targets**, not accepted SLA; record failures and seek Product/IT threshold disposition before release. No invented measured result.
- [ ] Commit tests/fixes/evidence in focused commits; release gate has no unresolved data-loss, target-misrouting, secret-leak or broken-core-flow defect. Baseline/environment exceptions require explicit disposition, not silent waiver.

## P5.2 — Installer, migration, upgrade và rollback

**Depends:** P5.1 candidate; Windows/architecture/admin/runtime/signing profile supplied by IT. **Files:** Inspect/modify only as needed `src-tauri/tauri.sds.conf.json`, `src-tauri/tauri.sds.dev.conf.json`, `scripts/sds.mjs`, existing SDS installer hooks discovered by inventory; extend `scripts/sds-installer.test.mjs`, `R/tests/migrations.rs`; create `docs/superpowers/evidence/phase5-installer.md`, `docs/superpowers/runbooks/upgrade-rollback.md`.

**Interface:** release inventory `{version, gitCommit, environment, architecture, toolVersions, dependencyLockHashes, configHash, installerPath, installerSha256, signatureStatus, testedOn}`. Changes to app version must use existing release preparation workflow after inspecting it; do not borrow upstream update feed.

- [ ] Record IT matrix exact Windows editions/builds/CPU architecture, standard-user/admin policy, WebView2 provisioning and signing requirements. Missing inputs block corporate acceptance only; continue owned local VM checks and clearly label limited coverage.
- [ ] Create copies of pilot DB/files and Phase 2–4 DB/files with real schema and synthetic data: multiple releases, local imports, presets, edited target and pending journal. Test migration/reopen and backup failure; assert count/ID/hash/reference invariants. Fail unknown future schema without rewriting it.
- [ ] Before migration provide bounded app-data backup/restore procedure with app stopped, SQLite consistent backup/WAL handling and manifest. Credentials remain in Windows vault; no plaintext credential export. Do not confuse user skill snapshots with a complete DB upgrade backup.
- [ ] Run existing installer regressions; any required change gets failing test first (e.g. no upstream CLI/fixtures/public updater, correct identifier). Build both artifacts:

```powershell
npm run sds:build -- --environment development --bundles nsis
npm run sds:build -- --environment internal --bundles nsis
```

Preserve development output before internal build because NSIS filenames can be reused. Store binary, hash and config outside generated output; no overwrite of last known good pilot artifacts.

- [ ] On disposable owned Windows profile/VM: clean install with/without pre-existing WebView2, launch without Internet, restart, upgrade from archived pilot to candidate, upgrade from previous candidate, repair/reinstall, uninstall. Assert app Library/config/presets/skill targets preserved per documented policy and upstream data untouched. If installer offers data deletion it must be explicit and tested only on synthetic data.
- [ ] Rollback rehearsal: stop app, restore previous binary **and matching pre-migration app-data backup** when schema is not backward compatible. Validate restored DB integrity + deployment reconciliation; preserve post-upgrade target files for review rather than silently overwriting edits. Document which target changes cannot be rolled back by installer alone. Candidate must not auto-open newer unsupported schema with old binary.
- [ ] Record native results, upgrade timing, hash inventory, signing status, WebView2 source and admin behavior. Pilot unsigned/WebView2-preinstalled result is not corporate packaging acceptance. Commit `docs(sds): verify installer upgrades and rollback` plus isolated required fixes.

## P5.3 — Network, permissions và support diagnostics

**Depends:** P5.1–2, corporate test endpoint/proxy/CA from IT. **Files:** Create `docs/superpowers/testing/phase5-environment.md`, `docs/superpowers/evidence/phase5-environment.md`, `docs/superpowers/runbooks/network-and-permissions.md`; if tests expose defects modify `R/store_client.rs`, `R/error.rs`, `R/profile.rs` and corresponding tests through red→green cycle.

- [ ] Test matrix: loopback HTTP dev accepted/internal rejected; internal HTTPS trusted CA success; untrusted/expired/name-mismatch cert rejected; proxy direct/auth-required/denied; DNS failure/timeout/interrupted package; session expiry vs 403; `/skm` context path retained; redirects cannot leak auth or escape approved origin.
- [ ] Inspect existing reqwest TLS/proxy behavior before choosing an implementation. If corporate CA/proxy unsupported, add minimal profile-supported configuration with tests and no disabled certificate validation. Do not change host trust store or expose proxy credentials in IPC/log/export.
- [ ] Windows permission cases: standard user, read-only project, controlled-folder denial, long/Unicode path, case aliases and junction replacement. Check path error includes selected target/actionable next step while keeping other deployments intact.
- [ ] Observe installed process/network while sign-in/catalog/install/local import/feed/export: no upstream Git/CLI child, public updater, CDN/font/image fetch. Record observation interval/process tree/destinations; a finite observation is not proof of all future traffic. Add deterministic profile tests for denied capabilities.
- [ ] Verify support export from P4.3 with synthetic secrets and malformed server errors; attach sanitizer tests. Instructions distinguish missing agent, missing MCP config, expired account, offline, insufficient permissions, corrupt package and recovery-required; never advise blanket TLS disable or deleting Library to fix errors.
- [ ] Run actual consumer/provider contract tests against dedicated local Store, ACL checks and Store additive before/after audits after final integration; do not start/reset shared DB. Preserve commands, process/port identity and file/schema manifests; no missing provider evidence accepted as pass.
- [ ] Commit environment evidence/runbook; mark blocked corporate scenarios explicitly with owner. Do not close release gate on local loopback tests alone.

## P5.4 — Bàn giao candidate và nghiệm thu

**Depends:** P5.1–3. **Files:** Create `docs/superpowers/releases/sds-1.0-acceptance.md`, `docs/superpowers/releases/sds-1.0-manifest.json`, `docs/superpowers/runbooks/user-guide.md`, `docs/superpowers/runbooks/support-guide.md`; update plan links/checklists only from evidence.

- [ ] Freeze final commit/version/config/lockfiles. Build in clean checkout with documented tool versions and dependency source/cache suitable for internal network. Record exact command and dependency resolution; repeat clean build to demonstrate reproducible procedure. Do not promise byte-for-byte identical unsigned/signed installers without measuring timestamps/signing effects.
- [ ] Verify artifact SHA-256 and signature after any signing step, and native smoke that exact artifact. Compare manifest commit/config/environment with the tested candidate. A rebuild/signing change invalidates old artifact hash even if source commit is unchanged.
- [ ] Assemble traceability table for every SRS ID with evidence pass/fail/blocked and accepted exception reference. Include full-suite baseline failures, ignored opt-ins, agent runtime limits, WebView2/admin/signing and performance findings; no untested item marked done.
- [ ] User guide: connection/login, four agents/global/project, MCP warning, Store/local install, Library/preset/bulk, update/edits/snapshot/restore, remove/cache, offline, internal app notice. Support guide: sanitized export, recovery decision tree, upgrade/rollback procedure, known issues and responsible team/contact supplied by owner (never invented).
- [ ] Prepare release notes, internal artifact location proposed by IT, pilot cohort/owner, staged rollout and rollback trigger proposal. No upload/publish/send to staff in this planning scope; distribution is a separate explicit release action after owners review concrete artifacts.
- [ ] Product validates core user flows, IT validates environment/signing/distribution, agent owners supply available runtime evidence. Preserve AIPro machine-local acceptance adjustment; any corporate-runtime limitation is written in release notes or explicitly accepted by the responsible owner.
- [ ] Commit `docs(sds): assemble 1.0 acceptance and support handoff`. Mark Phase 5 complete only when required acceptance evidence exists and remaining limitations have explicit disposition. A plan, mock UI, compiled installer or successful unit suite alone cannot close 1.0.

## Exit checklist

- [ ] G2, Phase 3, Phase 4 gates traceable to commits/evidence.
- [ ] Every required SRS case passed or has explicit accepted limitation; no critical open defect.
- [ ] Exact internal release artifact tested, hashed and signed per company policy.
- [ ] Clean install/upgrade/data preservation/rollback rehearsed on target matrix.
- [ ] Corporate network/proxy/CA/Windows permissions checked with no public fallback.
- [ ] User/support/runbook/manifest/release notes handed to named responsible owners.
- [ ] Rollout authorization separate from engineering acceptance; no claim of deployment before actual rollout.
